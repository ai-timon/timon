A slot is a named extension point owned by the component that renders it. `ctx.slots.register(options, Component)` returns a disposer. A registration can declare child slots; disposing it removes those children too.

| Slot kind | Composition |
| --- | --- |
| `list` | Multiple entries |
| `keyed` | Entries selected by key, such as a page route |
| `single` | One active occupant, with a product fallback where provided |

## Admission

Any slot ending in `.widget` is a general widget host. Declaring `cockpit.widget` admits the widget to other widget zones, including zones supplied by third-party layouts. The user can move it without reinstalling the package.

**Every other slot requires an exact declaration.** A widget does not gain access to `root`, `page`, `nav.item`, `nav.footer`, `settings.section` or `settings.missions`. Declaring one settings group does not open other groups.

`root` is the whole interface. Only a `layout` may declare it, and it is filled only under a licence that includes White Label; otherwise the product layout keeps it (see [Kinds](kinds.md#layouts-and-white-label)).

Registering in an undeclared or refused slot throws. The error identifies the requested surface and manifest slots.

## Slot lifetime

Register a normal widget in `cockpit.widget`. Chat widget zones are declared only while the chat page is mounted; use placement to move a widget there. Do not assume every destination exists when your plugin first loads.

For layout authors, a name ending in `.widget` promises to accept general widgets. Use a different name for a region requiring a specialised component contract. Render the slots you declare using the platform `Slot` or `SlotKeyed` components.

## Special surfaces

`agents.view` is keyed and requires exact admission. A registered view receives no props; the Agents shell retains its top bar, selector and widget zones. Use a stable key and release it when unloading.

`nav.item` is a list slot: one entry of the side menu. Register it with `key` set to your page's route (`ctx.slots.register({ slot: 'nav.item', key: '/growth' }, GrowthNav)`, lowercase, starting with `/`). The key is what the user's menu refers to: with it, your entry can be moved, hidden, separated and sent to the bottom of the menu like the product's, and it comes back to its place when your plugin is switched off and on again. Without a key it shows at the end of the main list and cannot be moved or hidden. While the user customizes the menu, Timon draws the row's grip and eye itself and makes your component inert: paint a plain link (icon and label) and leave hiding to Timon. The simplest entry is `NavLink` from `@timon/ui` (API 15): `() => h(NavLink, { href: '/growth', label: 'Growth', icon: GrowthIcon })`. It folds to its icon when the rail is folded, which a component of your own cannot know.

`nav.footer` is a list slot at the foot of the navigation, under the page entries (and under the pages the user moved to the bottom of the menu) and above the settings gear, in the rail and in the mobile drawer. It holds a control that applies to the whole interface rather than to one page. Declare it by exact name; declaring `nav.item` does not open it. Nothing is painted while it is empty.

`agents.toolbar` is a list slot for small controls of the **Agents** page: it is painted in its action bar. `onboarding.agent` is a list slot under the agent step of the onboarding, for another way in (for example, importing agents the person already has elsewhere). Declare each by exact name; a widget is refused there. The component receives no props; paint a small button. Nothing is painted while they are empty.

`bots.rail.action` is a list slot at the foot of the **TIMs** list, beside the search, **New TIM** and **New team**: paint one compact icon button (32 px square, `aria-label` set) with its name in a `Tooltip` from `@timon/ui`, wrapped in its own `TooltipProvider`, translated like the rest of your plugin. `agent.menu.item` is a list slot in the menu of one agent, opened by its **…** or a right click on its row in the **TIMs** list: paint a `DropdownMenuItem` from `@timon/ui`, and read the agent with `useAgentMenuItem()` (`{ name, role }`, `null` outside that slot; API 15) — the entry is registered once and rendered in every agent's menu. Declare each by exact name; nothing is painted while they are empty.

`agentimport.source` is a list slot opened by the built-in **Agent import** plugin, not by the layout: it exists while that plugin is on and is painted under the source cards of the import assistant. A source adapter for another tool registers there by exact name. The component receives no props: it reads the assistant with `useAgentImport()` from `@timon-ai/plugin-agent-import/hooks` (bundle it, keep `react` external; outside the assistant it returns `null`). The working path for a third party is to convert the other tool's export in the browser into a `timon-agent-import` v1 manifest, pack it alone as `timon-agent-import.json` at the root of a zip, and call `submitFile(id, zip)`: the import then shows its own preview and writes nothing before the user confirms. A secret travels by name only, never by value. The adapter never sees the staging token. `registerSource({ id, label, accepts, description })` adds a card whose file button sends the picked zip as it is, which only helps when the other tool already writes that manifest. Requires `apiVersion: 15`; template: `examples/plugin-agent-import-source`. What the import brings over is described in [Import agents](../usage/import-agents.md).

`kanban.column` is a list slot rendered before status columns. It is **not** a widget destination or a new task status. Supply your own header and body; the host supplies column geometry, not task-drop handling. Create tasks through an explicit authorised operation instead of suggesting that dropping onto a decorative column changes a task's status.

`kanban.todo.badge` and `kanban.todo.detail` are list slots on an idea of the TO DO notebook: a small read-only badge next to the idea (on its line in the TO DO widgets, its Kanban card and its detail), and a block in the detail dialog. Declare them by exact name in `client.slots`. The component receives no props: call `useTodoItem()` (badge) or `useTodoDetail()` (detail, returns `{ item, saved }`: call `saved()` after your own save so the notebook re-reads the idea) from `@timon/ui`. `item.links` holds the tickets the idea is tied to elsewhere.

`chat.document` is a single slot: the card of an HTML document in a conversation. It exists from startup, so a replacement registers in its `apply` whether a document is on screen or not. The component receives no props: call `useUiDocument()` from `@timon/ui`, and render `UiDocumentFrame` inside your card to keep the sandbox, the bridge and the focus guard ([HTML documents in a conversation](ui-documents.md)). Requires `apiVersion: 9`.

`dictation.engine` is a keyed slot that exists from startup: a [dictation engine](dictation.md) registers there with the `dictation` option, its key being the engine's id. It requires `kind: dictation`, the `dictation:engine` permission and `apiVersion: 14`; any other kind is refused. Its settings go in `settings.voice`, a list slot painted in **Settings → Interface → Voice dictation**.

`model.picker` is a single slot: the model selector of the whole interface — the chat composer, the task form, the agent editor and every other model field paint its occupant. It exists from startup; Timon's own picker is the fallback and comes back when your plugin is removed. The component receives no props: call `useModelPicker()` from `@timon/ui`, which returns the value, `onChange`, the optional `inherit` entry, `filter`, `footer`, `disabled`, the `className` to put on your root, and `mode` (`panel` or `popover`). In a popover Timon keeps the trigger, the anchoring, the focus and the closing: paint the content only; `onChange` closes it, unless `popover.keepOpenOnPick` says the surface closes it itself. Read the models with `useBackendCatalog()`: on a surface that chooses for an agent or a project, it already leaves out a provider that agent or project could not run on, and `useModelPicker().target` names who it is for. Keep three rules, which Timon also enforces on `onChange`: an account that cannot run (`isPickable` false) is shown but not choosable, the `inherit` entry hands back `null`, and a value whose provider left the catalogue stays shown, selected and disabled. Requires `apiVersion: 13`; template: `examples/plugin-model-picker`.

`providers.cli` is a single slot: the AI tool cards of the first-run **Your AIs** step, of its "cannot start" screen and of Settings › AI models › Providers. It exists from startup; Timon's own cards are the fallback and come back when your plugin is removed. The component receives no props: call `useProviderCliCards()` from `@timon/ui`, which returns `mode` (`onboarding`, `recovery` or `settings`), the `backends` (`null` while loading), `unavailable` (the viewer may not see them), the install `jobs` with the installer's console lines, `updateCheck`, `busy`, `disabled`, and four actions: `install(name)`, `refresh()`, `checkUpdates()` and `signIn(name)`, which types the tool's sign-in command in Timon's terminal (never pressing Enter) or copies it when the page has no terminal, and answers `terminal`, `copied` or `failed`. Timon runs the installer and follows it; your plugin names a tool, never a command. Offer **Install** only for a tool marked `installable`, link its `installDocs` otherwise, offer nothing to install or update for a tool marked `unsupportedVersion` (a version Timon does not support is installed), and show no update while `updateCheck` is false. Requires `apiVersion: 14`; template: `examples/plugin-provider-cards`.

The Plugins gallery lists `task.form` among the slots occupied by `@timon/kanban`, which supplies the default task form.

`task.form` is a single slot: the form that creates or edits a Kanban task, opened from the board, the Agents page and the agents grid. It exists from startup; Timon's own form is the fallback and comes back when your plugin is removed. The component receives no props: call `useTaskForm()` from `@timon/ui`, which returns `mode` (`create` or `edit`), the edited `task` (or `null`), `defaultAgent`, the `agents` the screen holds, `submit(body)` (creates or updates the task and answers its id, without closing), the `attachments` actions (`list`, `upload`, `remove`, `url`), `finish()` (the screen reloads its tasks and the form closes), `close()`, `remove` (deletes the edited task, confirmation included, and closes once it is gone; `null` where the screen offers no deletion) and `titleId`. Timon keeps the window around your form: the focus stays inside and goes back where it was, and Escape closes it (call `preventDefault()` on an Escape you handle yourself). Put `titleId` on your heading, and send back the fields you do not show as the task holds them, so saving never changes them. On edition, send `clear_fallback: true` to erase both fallback overrides, or `clear_permission_mode: true` to restore the agent's mode; these flags win over values in the same body. Without them, `null` keeps those stored overrides. Omit the flags on creation. Requires `apiVersion: 14`; template: `examples/plugin-task-form`.

`directory.picker` is a single slot: the folder browser that **Browse…** opens in Settings, a project or an agent whenever the window drives another machine through the machine selector, or runs in a web browser. It exists from startup; Timon's own browser is the fallback and comes back when your plugin is removed. On this computer in the desktop app, the system's folder dialog opens instead and the slot is not painted. The component receives no props: call `useDirectoryBrowser()` from `@timon/ui`, which returns `initialPath` (the folder the form holds, `''` when none), `opening()` (the first level: that folder when the machine can read it, otherwise its home), `read(path)` (one level of the machine's disk; `null` for its home), `choose(path)` and `cancel()`. A level comes back as `{ ok: true, listing }` — `path`, `parent` (`null` at a root), `entries` (`name`, `path`, `hidden`), `truncated`, `home`, `roots` (the drives on Windows) — or `{ ok: false, error }`: say why (`forbidden`, `unreadable`, `outdated` when that machine runs an older Timon…) rather than show an empty list. Every path is built by the daemon of the machine that will read it: hand back a `listing.path` or an `entry.path`, never one you put together. Timon keeps the window around your browser — its accessible name, the focus, Escape, and a submit that never reaches the form behind it. The same slot answers the file pickers — a plugin archive (**Plugins › Install a plugin**) and a CLI binary (**Settings › AI models › CLI binaries**) on another machine or in a web browser: `useDirectoryBrowser()` then returns `mode: 'file'` and `accept` (the endings the form takes, such as `.tgz`, already applied; `[]` for any file), and each level also carries `files` (`name`, `path`, `hidden`) and, when the form held a file that passes `accept`, `selected` (that file; the level is its folder — out of `accept`, the folder opens with nothing selected). In file mode `choose(path)` takes only a file Timon listed — a folder is ignored — and only a superadmin may list a machine's files. Requires `apiVersion: 15`; template: `examples/plugin-directory-picker`.

`confirm.dialog` is a single slot: the confirmation dialog of the whole interface — stopping a mission, deleting a task, a secret or an agent, replacing a licence. It exists from startup; Timon's own dialog is the fallback and comes back when your plugin is removed. The component receives no props: call `useConfirmDialog()` from `@timon/ui`, which returns the open question's `title`, `description` (`null` when none), `confirmLabel` and `cancelLabel` (already translated), `destructive` (the yes destroys or stops something), `confirm()` and `cancel()`. Timon keeps the window around your dialog: it is named with the question for screen readers, the focus stays inside and goes back where it was, and Escape or a click outside answers no. Do not add a `DialogTitle`, give the focus to the safe button so Enter right after the click cannot destroy anything, and always answer with `confirm()` or `cancel()`. To ask a confirmation of your own from any plugin, call `await confirmAction({ title, description, confirmLabel, destructive })` from `@timon/ui` — it resolves `true` only on an explicit yes, and questions asked meanwhile wait their turn; never use the browser's `confirm()`. Requires `apiVersion: 15`; template: `examples/plugin-confirm-dialog`.

`updates.banner` is a single slot: the banner at the top of the interface that announces a newer Timon. It exists from startup; Timon's own banner is the fallback and comes back when your plugin is removed. Timon only paints the slot while a newer version is published for the channel of the build and the person has not put it off, so your component never decides whether to show. It receives no props: call `useUpdateStatus()` from `@timon/ui`, which returns `installed`, `channel`, the `offer` (`version`, `publishedAt`, `notes`, `notesUrl` and every installer in `artifacts`), `installers` (the ones for the system of this browser, the first to download first; empty on a phone — link `offer.notesUrl` then), `buildExpiresAt`, `later()` and `download`. In the desktop app, `download` lets your banner drive the app's own verified download: show `download.state` (`idle`, `downloading` with `received` and `total`, `verifying`, `ready`, `failed` with a `code`) and offer `start()`, `cancel()`, `openFolder()`, `openInstaller()` and `install()`, none of which names a file; elsewhere it is `null`, so link the installer instead. `install()` installs the verified file the system's way; while missions are running it does nothing and answers `{ status: 'missions', count }`: say how many, and offer to wait or to call `install(true)`. Its other answers (`restarting`, `closing`, `opened`, `guided` with the `command` of a `.deb`, `not_writable`, `failed`) say what follows; `none` means the verified installer is no longer on disk and nothing was tried — offer `start()` again; `unsupported` comes from an older desktop app — call `openInstaller()` instead. The notes are plain text: show them as text, never as HTML. Offer `later()`: it hides this version only. While your banner is shown, Timon hides its own "this build stops running" notice, so say when the build stops if `buildExpiresAt` is set. Requires `apiVersion: 15`; template: `examples/plugin-update-banner`.

`apps.card` is a single slot: one card of the **official connectors**, at the head of the Connectors tab of Capabilities, painted once per connector. It exists from startup; Timon's own card is the fallback and comes back when your plugin is removed. The component receives no props: call `useAppCard()` from `@timon/ui`, which returns `app` (its `name`, `publisher`, `category`, `tagline`, `description` and `examples` already in the user's language, `auth` — `oauth`, `none`, or `key` with the key's `label` and the `helpUrl` where the publisher issues it — `links`, `icon` — a `color` tile with its `monogram` and, when the catalogue ships it, the publisher's `logo` as SVG path data (`viewBox`, `paths` of `{ d, fill? }`; a path without `fill` takes the ink that reads on the colour) —, and `mcpId`, the MCP server it is connected under), `status` (`available`, `connecting`, `consent` while the publisher's sign-in is not given yet, `connected`, `blocked` when an MCP server of the same name was added by hand), `consentUrl` (the sign-in page last opened, to offer again if the browser blocked the tab), `vaultOff`, and two actions: `connect(key?)` and `disconnect()`. Timon creates the server on the reviewed address, opens the sign-in page and keeps a key in the vault: never call the daemon from the card, ask an app of type `key` for its key in a masked field and pass it to `connect(key)`, and offer nothing on a `blocked` app. Requires `apiVersion: 15`; template: `examples/plugin-app-card`.

`mcp.featured` is a list slot: sections at the head of the Connectors tab of **Capabilities**, above the user's own MCP servers (Timon's official connectors live there). It exists from startup. The component receives no props: call `useMcpTab()` from `@timon/ui`, which returns `{ query }`, what the user typed in the tab's search field, so your section filters with it instead of adding a second search box (`null` outside the slot). Requires `apiVersion: 15`.

`page.toc` is a single slot: the table of contents in a sticky column on the left of the long list pages — the Skills and Connectors tabs of **Capabilities** — on wide screens. It exists from startup; Timon's own table is the fallback and comes back when your plugin is removed. The component receives no props: call `usePageToc()` from `@timon/ui`, which returns `entries` (each with its `id`, `label`, `level` — 1 for a section, 2 for a sub-section — and `count`, or `null`), in reading order and following the page's search, `active` (the section in view) and `go(id)`, which scrolls the page to it: jump with `go(id)`, never by scrolling yourself. A section of your own enters the table of any such page by its markup alone: give its heading an `id` and `data-toc="<label>"`, and optionally `data-toc-level="2"` and `data-toc-count="<n>"`. Requires `apiVersion: 15`; template: `examples/plugin-page-toc`.

`chat.message.action` is a list slot: the buttons under a chat message, after Timon's own **Copy**, **Copy as Markdown**, **Reply** and **Read aloud**. The chat declares it while it is on screen, so register it in your `apply` and let the chat paint it. Your component receives no props: `useChatMessage()` from `@timon/ui` returns the message it sits under — `role` (`agent` or `user`), `eventId` (`null` when no stored event backs the message: nothing can reply to it), `missionId`, `markdown` (the agent's Markdown source, or what the person typed) and `html` (the rendered, sanitized text) — and `null` elsewhere; return `null` on the messages your button has nothing to do with. Draw it with `MessageActionButton` (`label`, also its tooltip, `onClick`, `pressed`, `active`, the icon as children) so it looks like Timon's. `useComposerReply()` returns `{ reply, setReply }`: `setReply({ eventId, role, excerpt })` arms a reply exactly as **Reply** does, and a replacement composer reads `reply` and sends `reply_to: { event_id }` with the message. Requires `apiVersion: 15`; template: `examples/plugin-message-action`.

`agent.mascot` is a single slot: an agent's mascot, the plush meerkat head whose screen shows the agent's eyes. It exists from startup; Timon's own mascot is the fallback and comes back when your plugin is removed. Every screen that shows an agent's mascot paints it through this slot: the onboarding, agent creation, the avatars of agents everywhere in the app. The component receives no props: call `useAgentMascot()` from `@timon/ui`, which returns the agent's `look` (`shape`, `color` as `#rrggbb`, `eyes`, `acc` — always complete and valid; a field may hold a [mascot pack](mascot-pack.md)'s part, `<plugin>:<slug>`: draw an id you do not know with a default), `fur` (the colour to paint, as `#rrggbb`, a pack's fur included), `size` (paint a square of that many pixels), `live`, `state` (what the agent is doing, such as `thinking` or `waiting`, or how it reacts; `null` for none), `fit` (keep everything inside the square), `shadow`, `label` (the accessible name, or `null`: mark your drawing `aria-hidden`) and `reducedMotion`. `live` is already `false` when the person asked their system for reduced motion, turned off **Animate mascots**, or when the mascot is off screen or its agent asleep: never animate then, but still show `state`. Wherever an agent's head is its mascot — cards, rails, chat bubbles, Multichat, the Agents graph, the Kanban — `state` follows what the agent is doing (`sleeping`, `idle`, `thinking`, `working`, `searching`, `waiting`, briefly `happy` or `celebrate`); in menus it is `null`. Requires `apiVersion: 15`; template: `examples/plugin-mascot`.

`mascot.parts` is a keyed slot that paints nothing: the parts a [mascot pack](mascot-pack.md) adds to the mascot and its configurator — skulls, furs, eyes, accessories — registered as data with `ctx.slots.register({ slot: 'mascot.parts', key: '<slug>', mascotPart })` and no component. Each slug must be declared in the manifest's `mascot` block for that field; the entry is keyed `<plugin id>:<slug>`. It exists from startup. Requires `apiVersion: 15`; template: `examples/plugin-mascot-pack`.

`email.code` is a single slot: the screen where a person types the 6-digit code an email brought them — the confirmation of the first account during onboarding, and a forgotten password on the sign-in screen. It exists from startup; Timon's own six boxes are the fallback and come back when your plugin is removed. The component receives no props: call `useEmailCode()` from `@timon/ui`, which returns `purpose` (`verify` for the first account, `reset` for a forgotten password — for a reset, never say an account exists: Timon answers the same for any address), `email`, `length` (6), `digits` (typed so far), `input(value)`, `state` (`idle`, `checking`, `ok`, `bad`, `sent` or `failed`), `attemptsLeft`, `message` (the refusal, already worded in the reader's language, its wait counted down; `null` when there is none), `resendIn` (seconds before `resend()` opens), `resending`, `resend()` and `changeEmail()`. Pass everything typed or pasted to `input`: Timon keeps the digits and checks a complete code; never call Timon yourself. Requires `apiVersion: 15`; template: `examples/plugin-email-code`.

`agent.lookstyler` is a single slot: the mascot configurator — the live preview with states to try, the skull, fur, eyes and accessory choices, and a random draw. Two screens open it: the **Customise** panel of the first-run agent step and the **Avatar** tab of the agent editor, so replacing it changes both at once. It exists from startup; Timon's own configurator is the fallback and comes back when your plugin is removed. Paint the inside only: the panel or tab around it, its title and its **Done** belong to Timon. The component receives no props: call `useLookStyler()` from `@timon/ui`, which returns `look` (always complete and valid), `onChange(look)` (hand back a whole look), the agent's `name` and `role` (or `null`), `states` (the states Timon's preview offers), `choices` (`shapes`, `colors`, `eyes`, `accessories`: Timon's lists, then the parts of the [mascot packs](mascot-pack.md) installed), `packs` (those packs and their parts, to group them) and `random()`. Offer only what `choices` holds: a field off the lists keeps its current value. The slot name has no hyphen. Requires `apiVersion: 15`; template: `examples/plugin-look-styler`.

`kanban.card` is a single slot: the tile of a Kanban item, a TO DO idea or a task, on the board and in the lines of the TO DO widgets. One slot holds both kinds. The component receives no props: call `useKanbanCard()` from `@timon/ui`, which returns `density` (`card` on the board, `row` in a widget's list), `open()` (opens the item's window) and, depending on `kind`, either the idea — `kind: 'todo'`, `item`, `show` (whether the widget shows the `id`, the `author` and the `project`), `toggleDone`, `handoff` (hands the idea to its project's orchestrator; `null` for an idea without a project) and `remove` (`null` where the screen offers no such gesture) — or the task — `kind: 'task'`, `task`, `board` (every task by id, unfiltered), `now`, `agent`, `agentRole`, `todo` (the idea it carries out), `needsAction`, `dragging`, `modelTarget`, `drag`, `stop()`, `markMerged()`, `openGraph(focusId)` and `refresh()`. `todo.form` is a single slot, the twin of `task.form`: the window that creates or edits a TO DO idea, opened from the Kanban's TO DO column and the TO DO widgets. `settings.connection.form` is a keyed slot: your own form for one of your [connection types](connections.md), registered under the type id (`<plugin>:<name>@<version>`). It receives no props either: call `useConnectionForm()` from `@timon/ui`. The same form adds and edits a connection: its `mode` says which.
